* Stage 2: Formalize the Process of Capturing Updates to a system in rawBisos

<<Stage 2>>

Goal: Capture update and new features in the raw-bisos chain.

The ./raw-bisos.sh script is used to re-create the entirety of BISOS on a Fresh Debian System

When various features and CBMs are added, they need to be reflected in raw-bisos's chain.
There are container based re-creation facilities in /bxRepos/bxObjects/bro_dockerfiles/
that start from a fresh debian and run the entirety of ./raw-bisos.sh
These happen on VMs. When running in a container do NOT run ./raw-bisos.sh

Absorbing new features in the raw-bisos chain involves the following:

- When a pip-package is created or updated, it should be pushed to
  PyPi so that it can be pip and pipx installed.

- When a new pip-package is created, it should be added to
   /bisos/core/bsip/bin/rawBisos-sbom.pcs

- When a new repo has been created or deleted on github,
  it needs to be reflected in /bisos/git/bxRepos/bisos-pip/common/py3/bisos/common/

The abobe applies to the pure RawBisos, the process of adding RawBisosCbms will be added later.

Today (read 2026-11-02, Claude):
- The registry is Python: 197 gitClone / gitCloneBase lines in pbdDict_bxReposRoot. Adding or
  removing a repo means editing bisos.common and releasing it to PyPI before a fresh chain sees it.
- It is a curated selection, not every repo of an org: of bisos-pip's 85 GitHub repos 68 are
  listed; others are left out on purpose (marmee.obsolete, the defunc-*, the *.moved, the bulky
  aip_vagrantBaseBoxes.*) or simply forgotten (the 20 of 2.1).
- It maps names: local blee <- GitHub bx-blee, unisos <- bx-unisos, mohsenBanan <- ByStar/
  mohsenBananBase; and an org directory is itself a clone of that org's base repo (<org>/base, or
  bisos-web/.github), with the other repos cloned inside it.
- anon clones use git://github.com, which GitHub turned off in 2022; it works only through the
  "url.https://.insteadOf git://" that bisosAccounts_lib.sh sets. auth clones use an ssh alias
  (--gitLabel=mb1_github). Two sibling pbds stay out of scope here: bxReposCollection (the
  top-level directories and links) and extRepos (external repos).

gitist (bisos-pip/gitist) already has: a seed with planted .pcs per brand and access type (anon
https, auth by ssh alias = gitAccessAcct, or token); gitist_reposList (the org's repos from the
API), gitist_reposClone (every repo of an org), gitist_clone (one repo); existing clones skipped.

Proposed:
- One planted pcs per access type, e.g. bxRepos-anon-gitist.pcs and bxRepos-auth-gitist.pcs,
  whose csCmndsList is the registry as data: per org, its local directory, its base repo, and
  either "all but these" (exclusion patterns: *.moved, defunc-*, *.obsolete, archived) or an
  explicit list. "All but" makes a new GitHub repo appear without any edit, so rule 3 of Stage 2
  shrinks to keeping the exclusions.
- gitist gains what the registry has and it lacks: a local directory per org (blee for bx-blee),
  the base repo cloned as the org directory, exclusions, and a dry run (what would be cloned, and
  what is here but no longer on GitHub).
- bisosBaseDirs.sh runs the pcs instead of the bxReposRoot pbd; baseDirBxRepos.py's list is
  retired once a fresh chain (bro_dockerfiles, on a VM) clones the same tree.

Decided (Mohsen, 2026-11-02): the pcs live in /bisos/core/bsip/bin (bisos/bsip4), not in gitist's
